## M2-01 · Devnet deploy script: program, test-USDC mint, config
**Context:** First devnet presence; idempotent so it can be re-run safely.
**Satisfies:** FR-01, FR-22 (mint), FR-30 · NFR-14 · AB-22
**Build:** `scripts/deploy-devnet.ts` (+ `make deploy-devnet`), idempotent, in this order:
1. **Guards before any tx:** verify the cluster, independent of hostname: `getGenesisHash` must equal the devnet genesis hash (`EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`, kept in one shared constant), or `SOLANA_CLUSTER=localnet` with a loopback URL; any other genesis hash (mainnet, testnet, unknown) is refused, and so is an unreachable RPC (fail closed). This shared check is the one reused by M2-09; assert `pubkey(PROGRAM_KEYPAIR_PATH) == declare_id! in programs/meridian/src/lib.rs == IDL address == MERIDIAN_PROGRAM_ID` (when set), failing loudly otherwise (a mismatched keypair would deploy a program whose every instruction fails the declared-ID check, after SOL is spent). OQ-5 must hand over either the keypair for the existing declared ID (`3RovidBTwYzUfhniunxsUgnLzsbWz6qt3PGpvD23HDZq`), or approval to re-key: new `declare_id!` + `anchor keys sync` + rebuild in this MR (with a Decisions entry).
2. **Program:** `make build-devnet`, then deploy/upgrade using `PROGRAM_KEYPAIR_PATH` (path, never committed; documented in `docs/environment.md`). Upgrades sign with `ADMIN_KEYPAIR_PATH`. The first deploy passes the admin keypair as `--upgrade-authority` (a signer, not a pubkey), or runs an explicit `solana program set-upgrade-authority --new-upgrade-authority <admin pubkey>` step, so the fee payer never ends up as authority (custody is OQ-5).
3. **Test-USDC mint** (6 decimals, mint authority = `FAUCET_PUBKEY`), created if absent. "Absent" is decided on chain: a mint recorded in `deployments/devnet.json` (or `USDC_MINT`) is reused only after verifying on chain that it exists, has 6 decimals and mint authority == `FAUCET_PUBKEY`; if it exists but fails that check the script fails loudly and never creates a second mint over it. The mint keypair is generated and its pubkey written to the deployment record (write-ahead) before the create tx is sent. Recovery: a recorded mint that is absent on chain is treated as never created (nothing on chain references it) and is replaced by a fresh mint keypair, with a logged notice.
4. **Config** (back-to-back with the deploy, because `initialize_config` is first-come): `initialize_config` with admin, automation authority (`AUTOMATION_PUBKEY`; the script never reads `FAUCET_KEYPAIR` or `AUTOMATION_KEYPAIR`), staleness 30, conf 5 bps, override delay 3600 and the first 6 ticker slots (`MAX_TICKER_SLOTS_PER_CALL` = 6), then `update_config` for the 7th. On first run the feeds are **placeholders** (default pubkey, zeroed hash per source); M2-02 replaces them. On re-run the on-chain Config, not the deployment record, is the source of truth: the script reads the 7 tickers, never sends placeholders over non-default feeds, and rebuilds a missing or stale record from chain. `update_config` overwrites every scalar field, so the script always resends the current on-chain values for `automation_authority`, `usdc_mint`, `max_staleness_slots`, `max_conf_bps` and `override_delay_secs`, and lists only the ticker slots it changes, at most 6 per call. Feed fields are changed only by M2-02, which also goes through this script with two `update_config` calls (6 + 1).
5. **Deployment record** (program ID, mint, config PDA, feeds or placeholders; public keys only): default `deployments/devnet.json`, configurable via `--out <path>` or `DEPLOY_OUT`, so tests write to a temp dir and never touch the tracked file.

## M2-09 · Faucet
**Satisfies:** FR-22 · US-01 · NFR-13 · AB-21
**Build:** `POST /api/faucet {wallet}`: mints a fixed amount of test-USDC, devnet/localnet only (cluster verified by genesis hash with M2-01's shared check, not by hostname); faucet key from `FAUCET_KEYPAIR` (JSON array, server-only) and amount from `FAUCET_AMOUNT_USDC`, never in the bundle; header button "Get test-USDC". **Limit: 1 claim per wallet per 24 h (NFR-13), enforced atomically on chain with no program change, no off-chain store and no lock.** Let `dayBucket = floor(unix_ts / 86400)`. Each claim marks TWO buckets, N and N+1, in the same tx as the mint. Each marker is built as `SystemProgram.transfer` (rent-exempt lamports for space 1, paid by the faucet key) + `allocateWithSeed` (base = faucet key, seed = first 32 lowercase hex chars of `sha256(walletPubkey32 || bucket_u64_le)` (32 raw pubkey bytes followed by the bucket as an 8-byte little-endian u64; this encoding is pinned), space 1, owner = SystemProgram, so no separate `assignWithSeed` is needed). A second claim whose bucket is already marked fails atomically in `allocateWithSeed` (the account already has data), across any number of serverless instances. A claim at 23:59 on day N marks N and N+1, so a 00:01 claim (bucket N+1) fails; the guaranteed gap is at least 24 h of cluster time (the bucket is read from the cluster's latest confirmed block time at build time and the tx lands slightly later, so in wall time the gap can be shorter by a few seconds of lag), worst case about 48 h. Lamports pre-funded onto a marker address by a griefer do not block a claim (transfer tops up, allocate only needs empty data). Only the marker-already-in-use failure maps to 429: 429 iff the failing instruction index is one of the two marker-`allocateWithSeed` indexes (bucket N or N+1; indexes are computed from the built instruction list, so prepended ComputeBudget or ATA instructions do not shift them) AND the error is system-program `InstructionError` custom error 0 (`AccountAlreadyInUse`), whether it surfaces in preflight simulation or in the confirmed-tx error; any other error (including system-program failures from ATA creation or at other instruction indexes) is a 5xx with no mint. `unix_ts` comes from the cluster (`getBlockTime` of a recent slot, falling back to a confirmed slot's block time; never an instance wall clock), which every instance shares, so inter-instance clock skew cannot shorten the gap; the cluster clock is injected in tests. **Faucet SOL protection:** the faucet key's SOL balance has a floor (`FAUCET_MIN_LAMPORTS`, integer lamports, default 100000000 = 0.1 SOL): below it the endpoint returns 503 and mints nothing, and an alert is sent via `ALERT_WEBHOOK_URL` at most once per instance per cooldown (`FAUCET_ALERT_COOLDOWN_SEC`, default 3600; instance-local state, so several instances may each alert once per cooldown). A sybil drain with many fresh wallets (about 0.004 SOL each, not reclaimed) below that floor is accepted for devnet test tokens (OQ-17); no per-IP or global cap in M2. The wallet is parsed as a `PublicKey` and re-encoded before hashing (address casing/format cannot create a second marker). The faucet key pays the recipient ATA rent (create-idempotent) and the marker rent (two 1-byte rent-exempt accounts per claim, plus ATA rent, about 0.004 SOL in total, noted in the MR); devnet SOL for the faucet key is an operational need (runbook).
**Acceptance criteria:**
- [ ] AC1 Second claim for the same wallet within 24 h → 429 (local-validator test); fixed amount only. Gap is at least 24 h of cluster time (up to a few seconds of cluster-clock lag), worst case about 48 h; the UI error text says so.
- [ ] AC2 Refuses non-devnet clusters by genesis hash (tests with a mocked RPC: a devnet-hash URL on a non-standard hostname is allowed, a mainnet-hash URL is refused, an unreachable RPC is refused with no mint).
- [ ] AC3 `tests/security/ts/ab_21_faucet.test.ts` covers rate limit bypass attempts: address casing/encoding; two concurrent claims for one wallet (including from separate simulated instances) → exactly one mint; midnight boundary with the injected cluster clock: 23:59 then 00:01 → 429 (conflict on bucket N+1 only) and a conflict on bucket N only → 429, day N then day N+2 → allowed; two simulated instances with different wall-clock skews still get at least a 24 h gap (cluster time is used); a fixed known-answer vector pins the marker seed encoding (given a wallet pubkey and bucket, the seed and derived address equal hard-coded expected values, so a refactor cannot split the marker namespace); a pre-funded marker address does not block a claim (local validator); a non-marker system-program failure (e.g. ATA creation, or `AccountAlreadyInUse` at another instruction index) returns 5xx and mints nothing; below the SOL floor → 503, no mint, at most one alert per instance per cooldown (fake clock test); `FAUCET_MIN_LAMPORTS` is parsed as an integer (property test: rejects decimals, negatives, non-numeric).
- [ ] AC4 Faucet key never in client bundle (AC3 test extended).
- [ ] AC5 At startup / on the first request the faucet checks that the `FAUCET_KEYPAIR` pubkey equals the on-chain mint authority of `USDC_MINT` (and `FAUCET_PUBKEY` if set); a mismatch fails with a clear config error, not a 5xx on every claim (test with a mismatched key).
**Verification:** `pnpm --filter app test`, `make test-security`.
**Dependencies:** M2-01 (mint authority); confirmation of OQ-17 is not blocking the build.
**Files likely touched:** `app/src/app/api/faucet/**`, `app/src/components/faucet-button.tsx`, `tests/security/ts/ab_21_faucet.test.ts`.
