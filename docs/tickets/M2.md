## M2-01 · Devnet deploy script: program, test-USDC mint, config
**Context:** First devnet presence; idempotent so it can be re-run safely.
**Satisfies:** FR-01, FR-22 (mint), FR-30 · NFR-14 · AB-22
**Build:** a new pnpm workspace package `scripts/deploy` (name `deploy`; M2-11's deploy commands later live in the same package) owns `scripts/deploy/src/deploy-devnet.ts` and `scripts/deploy/src/lib/**` (+ `make deploy-devnet`). It declares its own dependencies, reusing the versions pinned in `tests/e2e/package.json` (`@coral-xyz/anchor` 0.31.1, `@meridian/client` workspace, `@solana/spl-token` 0.4.15, `@solana/web3.js` 1.99.0, `zod` 4.6.5, dev: `fast-check`, `tsx`), plus the workspace dependency `switchboard-scripts` (`workspace:*`, for `computeFeedHash`), so no new external dependency decision is needed; it has `typecheck`, `test`, `coverage` (`vitest run --coverage` with `thresholds: { lines: 80 }` in its `vitest.config.ts`, like `scripts/switchboard` and `packages/client`, so `make coverage` / `pnpm -r run coverage` enforces the floor instead of silently skipping the package) and `test:deploy` scripts. **Test split:** `test` = fast mocked unit and property tests (AC2 cluster-guard cases with a mocked RPC, `--feeds` validation including hash recomputation and ownership with mocked accounts, the program-ID and `.so`-hash guards, the skip-when-unchanged logic, idempotent record writing), which `pnpm -r run test` and `make test` run, with the vitest `include` set to `src/**/*.test.ts` and the heavy tests named `*.deploy.test.ts` under `test/deploy/` and excluded from `test` and `coverage` by `exclude`; `test:deploy` = the validator-backed AC1/AC3/AC6 tests (isolated copy, cold SBF build, `solana-test-validator`), reachable only through `make test-deploy-devnet`. Coverage and the 80% line floor are measured on `test` alone and must be met without the heavy tests; the heavy tests are never part of `pnpm -r run test` or `coverage`. Idempotent, in this order: guards, mint, program, Config, record.
1. **Build, then guards, all before any tx:** the script first runs the devnet build (the same command as `make build-devnet`, i.e. `anchor build`, executed with cwd = `--repo-root` rather than calling `make -C` on the real root, so it also works in the isolated copy, which has no Makefile; a cold SBF compile; a failed or slow build therefore leaves nothing on chain), reading and writing everything under an explicit `--repo-root <path>` (default: the real repo root; tests pass the isolated copy of step 6, so build, `declare_id!`, IDL, keypair and `.so` are all read from there and the shared `target/` is never rebuilt; the script alone builds, the tests do not pre-build in the copy). Before the first tx it asserts that the built `target/idl/meridian.json` has no `local_oracle_set` (AB-22) and that the `.so` it will deploy is that build (sha256 of `target/deploy/meridian.so` recorded right after the build and re-checked immediately before deploy; a stale local-oracle build left by `make test`, `make e2e` or `make client` must be rejected). This is the one place a local-oracle `.so` could reach devnet. Then it verifies the cluster, independent of hostname: `getGenesisHash` must equal the devnet genesis hash (`EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`, kept in one shared module, `packages/client/src/cluster.ts`, exporting `DEVNET_GENESIS_HASH` and `assertCluster({ cluster, rpcUrl, getGenesisHash })` (error messages and logs never contain the `rpcUrl` or any part of it, since provider URLs often carry API keys; they say `RPC` and the genesis hash only), importable by both `scripts/` and the app. M2-01 migrates `scripts/switchboard/src/devnet.ts` (which already holds `DEVNET_GENESIS_HASH` and `assertDevnet`) to import `DEVNET_GENESIS_HASH` and `assertCluster` from this module: `scripts/switchboard/package.json` and `pnpm-lock.yaml` gain the `@meridian/client` workspace dependency, `devnet.ts` re-exports `DEVNET_GENESIS_HASH` and keeps `assertDevnet(connection)` as a thin wrapper that calls `assertCluster({ cluster: "devnet", rpcUrl, getGenesisHash })` with `cluster` fixed to devnet (so a localnet genesis is still refused; `rpcUrl` is not consulted for `cluster: "devnet"`, and since `assertDevnet` only has a `getGenesisHash` connection it passes an empty placeholder) and preserves the error text `RPC is not Solana devnet (genesis <hash>); refusing to run`, which `devnet.test.ts` and `cli.test.ts` match with `/not Solana devnet/`, so existing callers and tests need no change, so there is exactly one copy of the constant; the switchboard-scripts tests keep passing unchanged. `assertCluster` takes the cluster name and RPC URL as parameters and has no `process.env` access (so the M1-12 bundle test, which fails on any documented server var such as `SOLANA_CLUSTER` in `.next/static`, cannot be tripped by `packages/client`); its callers (`scripts/`, the faucet route, `settle-now`) read `SOLANA_CLUSTER` and `SOLANA_RPC_URL` server-side and pass them in; M2-01's AC2 tests are that module's tests), or `SOLANA_CLUSTER=localnet` with a loopback URL; any other genesis hash (mainnet, testnet, unknown) is refused, and so is an unreachable RPC (fail closed). This shared check is the one reused by M2-09. It also asserts `pubkey(PROGRAM_KEYPAIR_PATH) == declare_id! in programs/meridian/src/lib.rs == IDL address == MERIDIAN_PROGRAM_ID` (when set), failing loudly otherwise (a mismatched keypair would deploy a program whose every instruction fails the declared-ID check, after SOL is spent). OQ-5 must hand over either the keypair for the existing declared ID (`3RovidBTwYzUfhniunxsUgnLzsbWz6qt3PGpvD23HDZq`), or approval to re-key: new `declare_id!` + `anchor keys sync` + rebuild in this MR (with a Decisions entry).
2. **Test-USDC mint** (6 decimals, mint authority = `FAUCET_PUBKEY`), created if absent. **Read the Config PDA first (chain is the source of truth):** if Config exists, take `usdc_mint` from it, verify on chain that it exists, has 6 decimals and mint authority == `FAUCET_PUBKEY`, and never create a mint, whatever `deployments/devnet.json` or `USDC_MINT` say (a missing or stale record is rebuilt from chain). Only when Config is absent is the mint decided from the record or `USDC_MINT`. "Absent" is decided on chain: a mint recorded in `deployments/devnet.json` (or `USDC_MINT`) is reused only after verifying on chain that it exists, has 6 decimals and mint authority == `FAUCET_PUBKEY`; if it exists but fails that check the script fails loudly and never creates a second mint over it. The mint keypair is generated and its pubkey written to the deployment record (write-ahead) before the create tx is sent. Recovery: a recorded mint that is absent on chain is treated as never created (nothing on chain references it) and is replaced by a fresh mint keypair, with a logged notice.
3. **Program:** deploy/upgrade the `.so` verified in step 1 using `PROGRAM_KEYPAIR_PATH`, **only when needed**: the script reads the on-chain ProgramData and compares it with the built `.so` by this exact rule: skip the 45-byte `UpgradeableLoaderState::ProgramData` header (4-byte tag, 8-byte slot, 33-byte `Option<Pubkey>`), require `len >= built_len`, require `data[..built_len] == built`, and require every byte after `built_len` to be zero (never trim on-chain trailing zeros, which breaks if the `.so` itself ends in zero bytes). A match means skip the deploy entirely (no buffer account, no upgrade tx, no SOL spent). **A mismatch against an existing program is not an automatic upgrade:** Anchor builds are not byte-reproducible across machines, and the M2-02 flow re-runs this script (with `--feeds`) from a possibly different worktree, machine or `main`, which could silently upgrade the live devnet program mid-rehearsal. So an upgrade is opt-in via `--allow-upgrade`; without it a mismatch fails loudly, printing both sha256 values, and sends no tx. A re-run on the same inputs sends no tx. `PROGRAM_KEYPAIR_PATH` is a path, never committed, and documented in `docs/environment.md`. Upgrades sign with `ADMIN_KEYPAIR_PATH`. The first deploy passes the admin keypair as `--upgrade-authority` (a signer, not a pubkey) in the deploy command itself, so the fee payer never ends up as authority and there is no separate post-deploy `set-upgrade-authority` step (which would reopen a window; custody is OQ-5). The deploy/upgrade goes through an injectable `runSolana` function wrapping the `solana` CLI, so tests can observe it. **The CLI never uses its own config:** the `solana` CLI is a separate process whose cluster and fee payer come from `~/.config/solana/cli/config.yml` and `~/.config/solana/id.json` unless told otherwise, so a machine whose CLI points at mainnet-beta would pass the web3 genesis guard and then spend real SOL there. Every `runSolana` call therefore passes `--url <the exact RPC URL the guard validated>` and `--keypair $ADMIN_KEYPAIR_PATH` (fee payer = admin, matching the `config.admin == ADMIN` check), plus `--program-id` / `--upgrade-authority` as above, and CLI stdout/stderr that is logged or thrown goes through the same URL redaction as AC2b (the CLI echoes the URL on RPC errors). Before writing a buffer for an upgrade, the script reads ProgramData and requires its upgrade authority to equal the admin pubkey, otherwise the upgrade would fail after the buffer account has already spent SOL.
4. **Config** (immediately after the deploy, because `initialize_config` is first-come; the mint is created before the deploy precisely so that no other transaction sits between the deploy and `initialize_config`, narrowing the front-run window to the gap between the deploy's final tx and the `initialize_config` tx; it does not close it, because `initialize_config` is first-come and makes the payer admin with no authority check, and if someone else wins that gap the Config PDA is theirs permanently and the only recovery is a re-key per OQ-5): `initialize_config` with admin, automation authority (`AUTOMATION_PUBKEY`; the script never reads `FAUCET_KEYPAIR` or `AUTOMATION_KEYPAIR`), staleness 30, conf 5 bps, override delay 3600 and the first 6 ticker slots (`MAX_TICKER_SLOTS_PER_CALL` = 6), then `update_config` for the 7th. On first run the feeds are **placeholders** (default pubkey, zeroed hash per source); M2-02 replaces them. On re-run the on-chain Config, not the deployment record, is the source of truth: the script reads the 7 tickers, never sends placeholders over non-default feeds, and rebuilds a missing or stale record from chain. `update_config` overwrites every scalar field, so the script always resends the current on-chain values for `automation_authority`, `usdc_mint`, `max_staleness_slots`, `max_conf_bps` and `override_delay_secs`, and lists only the ticker slots it changes, at most 6 per call. Real feeds come in through an optional `--feeds <file>` input (JSON `{ticker: [{pubkey, hash}, {pubkey, hash}]}` for 7 tickers × 2 sources, written by M2-02's `create-feeds.ts`); the script recomputes every hash as `sha256(queue || serialized job definition)` with `computeFeedHash` from `scripts/switchboard/src/spike.ts` (the pinned-hash function `cli.ts` already uses) over the job definitions in `oracle/feeds/*` and the Switchboard queue pubkey (`SWITCHBOARD_QUEUE`, documented for scripts, or `--queue <pubkey>`; the `--feeds` file carries no queue), and rejects any file whose hash differs; it also validates every pubkey as a Switchboard-owned account and reads each feed account's own `feed_hash` (the 32 bytes at `FEED_HASH_OFFSET` = `8 + 2112`, the layout `oracle.rs` and `generate_fixture.py` use), requiring it to equal the hash being pinned (a swapped or wrong-queue pubkey would otherwise only fail at settlement with `OracleFeedHashMismatch`), all before sending anything, then replaces the placeholders with two `update_config` calls (6 + 1). Without `--feeds` feed fields are never touched. Re-running with the same file is a no-op (no tx sent).
5. **Deployment record** (program ID, mint, config PDA, feeds or placeholders; public keys only): default `deployments/devnet.json`, configurable via `--out <path>`, so tests write to a temp dir and never touch the tracked file.
6. **Local-validator test setup (no OQ-5 secret needed), isolated from the shared tree:** the devnet-build test never touches the shared `target/` or the tracked files, because the rest of `make test` and `make test-security` use the local-oracle build in the same `target/` and run packages concurrently under `pnpm -r`. It therefore (a) runs as its own serial Make target (`make test-deploy-devnet`, added to `Makefile` by this ticket, not inside `pnpm -r`, and deliberately NOT part of `make test` or the DoD gate, because a cold devnet SBF build on every run would hurt the 1-vCPU CI runner and NFR-18; no `.gitlab-ci.yml` change from this ticket, that file is human-owned); and (b) works in a temporary copy of the repo's build inputs, copied from the working tree so uncommitted edits are included: `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` (so the pinned toolchain, channel 1.99.0, is used), `Anchor.toml`, `programs/`, `crates/`, `tests/security/program/` (the root `Cargo.toml` workspace lists `programs/meridian`, `crates/meridian-book` and `tests/security/program` as members, and cargo and `anchor build` fail if one is missing), plus any other path those crates read from the repo root (e.g. `tests/fixtures/`; the test fails loudly if the copy cannot build). No `CARGO_TARGET_DIR` is set: the copy's own default `target/` is already isolated from the real tree's, so the copy's `target/deploy/meridian-keypair.json` (where `anchor keys sync` reads it), `target/deploy/meridian.so` and `target/idl/meridian.json` all live under the copy. In that copy it follows `scripts/e2e.sh`: generate a throwaway program keypair at `target/deploy/meridian-keypair.json` of the copy (the only path `anchor keys sync` reads), run `anchor keys sync` so `declare_id!`, `Anchor.toml` and the IDL address match it, and build with `make build-devnet`-equivalent flags. The program-ID guard therefore runs unchanged against the throwaway ID, and no restore trap or dirty-tree guard is needed for the real tree because it is never modified. The copy is deleted on EXIT/INT/TERM. The test asserts, by before/after comparison (never an absolute state): a snapshot of `git status --porcelain` plus `git diff` taken before the run equals the one taken after, so uncommitted developer edits (which the copy deliberately includes) do not fail it; and the sha256 of the shared `target/deploy/meridian.so` and `target/idl/meridian.json` is unchanged, where a file absent before must be absent after (not an error; `target/` is gitignored, so a standalone run on a fresh checkout has no local build). ## M2-09 · Faucet
**Satisfies:** FR-22 · US-01 · NFR-13 · AB-21
**Build:** `POST /api/faucet {wallet}`: mints a fixed amount of test-USDC, devnet/localnet only (cluster verified by genesis hash with the shared `assertCluster` from `packages/client/src/cluster.ts` (M2-01), called by the route handler with the server-side `SOLANA_CLUSTER` and `SOLANA_RPC_URL` (never `NEXT_PUBLIC_*`), not by hostname and not duplicated in the app); faucet key from `FAUCET_KEYPAIR` (JSON array, server-only) and amount from `FAUCET_AMOUNT_USDC`, never in the bundle; a "Get test-USDC" button exported as a component (`faucet-button.tsx`). Each claim marks TWO buckets, N and N+1, in the same tx as the mint. Each marker is built as `SystemProgram.transfer` (rent-exempt lamports for space 1, paid by the faucet key) + `allocateWithSeed` (base = faucet key, seed = first 32 lowercase hex chars of `sha256(walletPubkey32 || bucket_u64_le)` (32 raw pubkey bytes followed by the bucket as an 8-byte little-endian u64; this encoding is pinned), space 1, owner = SystemProgram, so no separate `assignWithSeed` is needed). A second claim whose bucket is already marked fails atomically in `allocateWithSeed` (the account already has data), across any number of serverless instances. A claim at 23:59 on day N marks N and N+1, so a 00:01 claim (bucket N+1) fails; the guaranteed gap is at least 24 h of cluster time (the bucket is read from the cluster's latest confirmed block time at build time and the tx can land any time within its validity window, so the stated bound is **24 h minus W**, where W is the blockhash lifetime (about 150 blocks, 60 to 90 s; fixed by the recent blockhash, not settable by the server): an already-sent signed tx can still land until its blockhash expires. The server fetches a fresh blockhash per attempt, stops rebroadcasting at or before `lastValidBlockHeight`, and rebuilds the buckets from fresh cluster time on every new attempt, never reusing a signed tx from an earlier attempt; the NFR-13 target is met to within W), worst case about 48 h. Lamports pre-funded onto a marker address by a griefer do not block a claim (transfer tops up, allocate only needs empty data). Only the marker-already-in-use failure maps to 429: 429 iff the failing instruction index is one of the two marker-`allocateWithSeed` indexes (bucket N or N+1; indexes are computed from the built instruction list, so prepended ComputeBudget or ATA instructions do not shift them) AND the error is system-program `InstructionError` custom error 0 (`AccountAlreadyInUse`), whether it surfaces in preflight simulation or in the confirmed-tx error; any other error (including system-program failures from ATA creation or at other instruction indexes) is a 5xx with no mint. `unix_ts` comes from the cluster (`getBlockTime` of a recent slot, falling back to a confirmed slot's block time; never an instance wall clock), which every instance shares, so inter-instance clock skew cannot shorten the gap; the cluster clock is injected in tests. **Faucet SOL protection:** the faucet key's SOL balance has a floor (`FAUCET_MIN_LAMPORTS`, integer lamports, default 100000000 = 0.1 SOL): below it the endpoint returns 503 and mints nothing, and an alert is sent via `ALERT_WEBHOOK_URL` at most once per instance per cooldown (`FAUCET_ALERT_COOLDOWN_SEC`, default 3600; instance-local state, so several instances may each alert once per cooldown). A sybil drain with many fresh wallets (about 0.004 SOL each, not reclaimed) below that floor is accepted for devnet test tokens (OQ-17); no per-IP or global cap in M2. The wallet is parsed as a `PublicKey` and re-encoded before hashing (address casing/format cannot create a second marker). The faucet key pays the recipient ATA rent (create-idempotent) and the marker rent (two 1-byte rent-exempt accounts per claim, plus ATA rent, about 0.004 SOL in total, noted in the MR); devnet SOL for the faucet key is an operational need (runbook).

## M2-14 (PROPOSAL, needs Paawan approval) · On-chain market open_ts
**Status: NOT APPROVED, NOT STARTED.** Draft only; no worker picks this up and no code depends on it until Paawan approves it and the orchestrator moves it into the active ticket list.
**Context:** `docs/domain.md` says markets are visible from 09:00 ET and open at 09:30 ET, but the program has no open time: `Market` has no `open_ts`, and mint and orders are blocked only by pause and `now >= close_ts`. D-050 therefore has the UI show the market's real creation time as its open time rather than fake a 09:30 gate. A real 09:30 ET open needs the program to enforce it.
**Satisfies:** FR-13, FR-17 (open state) · AB-11 family (time gates)
**Build (proposal):**
- `Market.open_ts: i64` set at creation from the trading calendar (09:30 ET on the trading date, `America/New_York`, DST-correct), passed by the automation authority in `create_strike_market` and validated on chain against the market's `trading_date` and `close_ts` (`open_ts < close_ts`).
- `mint_pair`, `place_order`, `buy_no` and `sell_no` reject with a new `MeridianError::MarketNotOpen` when `now < open_ts`; `cancel_order`, `settle_funds` and redeem paths are unaffected. Emit `open_ts` in the `MarketCreated` event.
- Account-size change: `Market` grows by 8 bytes; devnet markets created before the upgrade are not migrated (they have no `open_ts`; see the open question below).
- Client and IDL regenerated (`make client`); UI-03 and M2-06 switch "open time" from creation time to `open_ts` and add a "Not open yet" badge with the countdown (a follow-up UI change, not part of this ticket).
**Acceptance criteria (proposal):**
- [ ] AC1 `create_strike_market` stores `open_ts`; a call with `open_ts >= close_ts` or an `open_ts` that does not match the trading date's 09:30 ET fails with a specific error.
- [ ] AC2 Mint and orders before `open_ts` fail with `MarketNotOpen`; at and after `open_ts` they succeed; cancel, settle_funds and redeem before `open_ts` are unaffected.
- [ ] AC3 `MarketCreated` carries `open_ts`; the generated client and IDL are committed (`make client`).
- [ ] AC4 Property test over trading dates (including DST changes and early-close days) that `open_ts` is 09:30 ET and strictly before `close_ts`.
**Abuse-case tests (`tests/security/`, named by AB ID):** extend `ab_11_close_pause` (orders and mint before open and after close are rejected); a new case that a non-authority cannot create a market with a chosen `open_ts`; a case that an `open_ts` in the past or after `close_ts` is rejected; the AB-22 devnet-build check is unchanged.
**Open questions for Paawan:** (1) migrate or leave devnet markets created before the upgrade (default: leave, they never gate); (2) the morning job creates markets at 08:00 ET and visible from 09:00: confirm the "visible 09:00" part stays UI-only.
