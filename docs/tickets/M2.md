## M2-01 · Devnet deploy script: program, test-USDC mint, config
**Context:** First devnet presence; idempotent so it can be re-run safely.
**Satisfies:** FR-01, FR-22 (mint), FR-30 · NFR-14 · AB-22
**Build:** `scripts/deploy-devnet.ts` (+ `make deploy-devnet`), idempotent, in this order:
1. **Guards before any tx:** verify the cluster, independent of hostname: `getGenesisHash` must equal the devnet genesis hash (`EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG`, kept in one shared module, `packages/client/src/cluster.ts`, exporting `DEVNET_GENESIS_HASH` and `assertCluster({ cluster, rpcUrl, getGenesisHash })`, importable by both `scripts/` and the app. `assertCluster` takes the cluster name and RPC URL as parameters and has no `process.env` access (so the M1-12 bundle test, which fails on any documented server var such as `SOLANA_CLUSTER` in `.next/static`, cannot be tripped by `packages/client`); its callers (`scripts/`, the faucet route, `settle-now`) read `SOLANA_CLUSTER` and `SOLANA_RPC_URL` server-side and pass them in; M2-01's AC2 tests are that module's tests), or `SOLANA_CLUSTER=localnet` with a loopback URL; any other genesis hash (mainnet, testnet, unknown) is refused, and so is an unreachable RPC (fail closed). This shared check is the one reused by M2-09; assert `pubkey(PROGRAM_KEYPAIR_PATH) == declare_id! in programs/meridian/src/lib.rs == IDL address == MERIDIAN_PROGRAM_ID` (when set), failing loudly otherwise (a mismatched keypair would deploy a program whose every instruction fails the declared-ID check, after SOL is spent). OQ-5 must hand over either the keypair for the existing declared ID (`3RovidBTwYzUfhniunxsUgnLzsbWz6qt3PGpvD23HDZq`), or approval to re-key: new `declare_id!` + `anchor keys sync` + rebuild in this MR (with a Decisions entry).
2. **Program:** `make build-devnet`, then deploy/upgrade using `PROGRAM_KEYPAIR_PATH` (path, never committed; documented in `docs/environment.md`). Upgrades sign with `ADMIN_KEYPAIR_PATH`. The first deploy passes the admin keypair as `--upgrade-authority` (a signer, not a pubkey), or runs an explicit `solana program set-upgrade-authority --new-upgrade-authority <admin pubkey>` step, so the fee payer never ends up as authority (custody is OQ-5).
3. **Test-USDC mint** (6 decimals, mint authority = `FAUCET_PUBKEY`), created if absent. **Read the Config PDA first (chain is the source of truth):** if Config exists, take `usdc_mint` from it, verify on chain that it exists, has 6 decimals and mint authority == `FAUCET_PUBKEY`, and never create a mint, whatever `deployments/devnet.json` or `USDC_MINT` say (a missing or stale record is rebuilt from chain). Only when Config is absent is the mint decided from the record or `USDC_MINT`. "Absent" is decided on chain: a mint recorded in `deployments/devnet.json` (or `USDC_MINT`) is reused only after verifying on chain that it exists, has 6 decimals and mint authority == `FAUCET_PUBKEY`; if it exists but fails that check the script fails loudly and never creates a second mint over it. The mint keypair is generated and its pubkey written to the deployment record (write-ahead) before the create tx is sent. Recovery: a recorded mint that is absent on chain is treated as never created (nothing on chain references it) and is replaced by a fresh mint keypair, with a logged notice.
4. **Config** (back-to-back with the deploy, because `initialize_config` is first-come): `initialize_config` with admin, automation authority (`AUTOMATION_PUBKEY`; the script never reads `FAUCET_KEYPAIR` or `AUTOMATION_KEYPAIR`), staleness 30, conf 5 bps, override delay 3600 and the first 6 ticker slots (`MAX_TICKER_SLOTS_PER_CALL` = 6), then `update_config` for the 7th. On first run the feeds are **placeholders** (default pubkey, zeroed hash per source); M2-02 replaces them. On re-run the on-chain Config, not the deployment record, is the source of truth: the script reads the 7 tickers, never sends placeholders over non-default feeds, and rebuilds a missing or stale record from chain. `update_config` overwrites every scalar field, so the script always resends the current on-chain values for `automation_authority`, `usdc_mint`, `max_staleness_slots`, `max_conf_bps` and `override_delay_secs`, and lists only the ticker slots it changes, at most 6 per call. Real feeds come in through an optional `--feeds <file>` input (JSON `{ticker: [{pubkey, hash}, {pubkey, hash}]}` for 7 tickers × 2 sources, written by M2-02's `create-feeds.ts`); the script validates every hash against `oracle/feeds/*` and every pubkey as a Switchboard-owned account before sending anything, then replaces the placeholders with two `update_config` calls (6 + 1). Without `--feeds` feed fields are never touched. Re-running with the same file is a no-op (no tx sent).
5. **Deployment record** (program ID, mint, config PDA, feeds or placeholders; public keys only): default `deployments/devnet.json`, configurable via `--out <path>`, so tests write to a temp dir and never touch the tracked file.
6. **Local-validator test setup (no OQ-5 secret needed):** the tests follow `scripts/e2e.sh`: generate a throwaway program keypair (in a temp dir or `target/deploy/`, never committed), run `anchor keys sync` so `declare_id!`, `Anchor.toml` and the IDL address match it, build with `make build-devnet`, and restore the tracked `programs/meridian/src/lib.rs` and `Anchor.toml` from an exit trap on EXIT/INT/TERM (same restore trap as `e2e.sh`). The program-ID guard therefore still runs unchanged against the throwaway ID. Tests assert `git status` shows no change to tracked files afterwards. The real `3Rovid...` keypair is needed only for the live devnet run (OQ-5).

## M2-04 · Automation settlement job
**Context:** Settle every open market from Switchboard at close + 5 min; retry; alert.
**Satisfies:** FR-14 · US-14 · NFR-04, NFR-06 · AB-03, AB-04, AB-05
**Build:** `services/automation/src/jobs/settle.ts`: at close + 5 min (early-close aware), verify off-chain both sources' latest bar date = trading date, build one tx per ticker: two Switchboard feed update ixs + `settle_market` for each open market; retry every 30 s for 15 min; then alert and `POST /incidents` to ops-agent (stub client until M3). **Local oracle path:** `services/automation/src/switchboard.ts` exposes an oracle-update adapter with two implementations, Switchboard feed-update instructions and the program's `local_oracle_set` for the local validator; the local one is selected only by the `assertCluster` localnet guard, is test-only, and is unreachable on devnet (AB-22: the devnet build has no `local_oracle_set`). AC1, AC7 and the job's local tests use the local adapter; AC4 and AC5 are Switchboard-only tx-builder tests. **Signer:** `AUTOMATION_KEYPAIR` is the fee payer and the `payer` signer of `settle_market`, and signs the Switchboard feed-update instructions; it must be loaded and funded (balance checked at startup and before each settle, low balance alerts). A pubkey mismatch with `config.automation_authority` does not matter for settlement (the program never reads it); a missing or unparseable key does (see M2-03 AC5b). There is no second always-loaded secret: the fallback is a manual **`settle-now` CLI** (`pnpm --filter automation settle-now --payer <keypair path> [--date YYYY-MM-DD]`) that runs the same settlement path (off-chain date verification, feed updates, `settle_market`, idempotent) with ANY funded devnet keypair supplied at run time, since `settle_market` is permissionless; the key path is never logged. Idempotent (skips settled markets). If one tx per ticker (two Switchboard updates plus N `settle_market`) exceeds the transaction size limit, fall back to a versioned tx with an address lookup table, and if still too large split into a feed-update tx followed by `settle_market` txs within the staleness budget (`max_staleness_slots` = 30 slots, about 12 s; domain.md), sent back-to-back, with a re-update of the feeds if the slot gap is exceeded.
**Acceptance criteria:**
- [ ] AC1 On the local validator with the local oracle, all open markets of a ticker settle in one run (test).
- [ ] AC2 Date mismatch → no settle tx sent; retries; alert after 15 min (fake timers).
- [ ] AC3 Re-run after success sends nothing (NFR-05).
- [ ] AC4 Tx builder places feed updates before `settle_market` and passes the Config-pinned feeds (unit test against a recorded fixture; no network).
- [ ] AC5 An oversized tx is split per the fallback above (unit test with a 7-market fixture), and the split path is tested against the 30-slot budget (simulated slot gap triggers a feed re-update, never an `OracleStale` send).
- [ ] AC6 Abuse cases AB-03/04/05 each have a test in `tests/security/ts/` named after its ID, matching threat-model.md and M1-07: `ab_03_*` stale value or yesterday's close (stale on-chain update is never sent to settle; the off-chain wrong-date check sends nothing), `ab_04_*` spoofed or unpinned feed (the tx builder only passes the Config-pinned feeds; a different feed is rejected by the program), `ab_05_*` settle before close (the job never sends before close + 5 min with a fake clock, and the program rejects an early `settle_market` with `MeridianError::NotClosed`, local-validator test).
- [ ] AC7 The `settle-now` CLI settles all open markets on the local validator using a payer that is not the automation key (test), skips already-settled markets, refuses a non-devnet/localnet cluster via `assertCluster`, and never prints the keypair path contents.
**Verification:** `pnpm --filter automation test`, `make e2e`.
**Dependencies:** M2-02 for live; M1-07.
**Files likely touched:** `services/automation/src/jobs/settle.ts`, `services/automation/src/switchboard.ts`, `services/automation/src/settle-now.ts`, `services/automation/package.json` (script), `services/automation/test/**`, `tests/security/ts/ab_0{3,4,5}_*`.

**Build:** `POST /api/faucet {wallet}`: mints a fixed amount of test-USDC, devnet/localnet only (cluster verified by genesis hash with the shared `assertCluster` from `packages/client/src/cluster.ts` (M2-01), called by the route handler with the server-side `SOLANA_CLUSTER` and `SOLANA_RPC_URL` (never `NEXT_PUBLIC_*`), not by hostname and not duplicated in the app); faucet key from `FAUCET_KEYPAIR` (JSON array, server-only) and amount from `FAUCET_AMOUNT_USDC`, never in the bundle; a "Get test-USDC" button exported as a component (`faucet-button.tsx`). UI-02 owns `layout.tsx` and `app-shell.tsx`, so this ticket starts only after UI-02 has merged and then touches `app-shell.tsx` for the single line that mounts the button in the header slot (sequential, never in parallel with another ticket editing the shell). **Limit: 1 claim per wallet per 24 h (NFR-13), enforced atomically on chain with no program change, no off-chain store and no lock.** Let `dayBucket = floor(unix_ts / 86400)`. Each claim marks TWO buckets, N and N+1, in the same tx as the mint. Each marker is built as `SystemProgram.transfer` (rent-exempt lamports for space 1, paid by the faucet key) + `allocateWithSeed` (base = faucet key, seed = first 32 lowercase hex chars of `sha256(walletPubkey32 || bucket_u64_le)` (32 raw pubkey bytes followed by the bucket as an 8-byte little-endian u64; this encoding is pinned), space 1, owner = SystemProgram, so no separate `assignWithSeed` is needed). A second claim whose bucket is already marked fails atomically in `allocateWithSeed` (the account already has data), across any number of serverless instances. A claim at 23:59 on day N marks N and N+1, so a 00:01 claim (bucket N+1) fails; the guaranteed gap is at least 24 h of cluster time (the bucket is read from the cluster's latest confirmed block time at build time and the tx can land any time within its validity window, so the stated bound is **24 h minus W**, where W is the blockhash lifetime (about 150 blocks, 60 to 90 s; fixed by the recent blockhash, not settable by the server): an already-sent signed tx can still land until its blockhash expires. The server fetches a fresh blockhash per attempt, stops rebroadcasting at or before `lastValidBlockHeight`, and rebuilds the buckets from fresh cluster time on every new attempt, never reusing a signed tx from an earlier attempt; the NFR-13 target is met to within W), worst case about 48 h. Lamports pre-funded onto a marker address by a griefer do not block a claim (transfer tops up, allocate only needs empty data). Only the marker-already-in-use failure maps to 429: 429 iff the failing instruction index is one of the two marker-`allocateWithSeed` indexes (bucket N or N+1; indexes are computed from the built instruction list, so prepended ComputeBudget or ATA instructions do not shift them) AND the error is system-program `InstructionError` custom error 0 (`AccountAlreadyInUse`), whether it surfaces in preflight simulation or in the confirmed-tx error; any other error (including system-program failures from ATA creation or at other instruction indexes) is a 5xx with no mint. `unix_ts` comes from the cluster (`getBlockTime` of a recent slot, falling back to a confirmed slot's block time; never an instance wall clock), which every instance shares, so inter-instance clock skew cannot shorten the gap; the cluster clock is injected in tests. **Faucet SOL protection:** the faucet key's SOL balance has a floor (`FAUCET_MIN_LAMPORTS`, integer lamports, default 100000000 = 0.1 SOL): below it the endpoint returns 503 and mints nothing, and an alert is sent via `ALERT_WEBHOOK_URL` at most once per instance per cooldown (`FAUCET_ALERT_COOLDOWN_SEC`, default 3600; instance-local state, so several instances may each alert once per cooldown). A sybil drain with many fresh wallets (about 0.004 SOL each, not reclaimed) below that floor is accepted for devnet test tokens (OQ-17); no per-IP or global cap in M2. The wallet is parsed as a `PublicKey` and re-encoded before hashing (address casing/format cannot create a second marker). The faucet key pays the recipient ATA rent (create-idempotent) and the marker rent (two 1-byte rent-exempt accounts per claim, plus ATA rent, about 0.004 SOL in total, noted in the MR); devnet SOL for the faucet key is an operational need (runbook).
